# MReact-03. Приоритет ввода через useTransition

React 19.3.1, Vite 8.3.8, Node 24.

```bash
npm install
npm run dev -- --host 127.0.0.1
```

Страница: https://dastan26.github.io/react-homework/MReact-03/

## Что сделал

За основу взят базовый поиск из условия: 240 вымышленных карточек, искусственная нагрузка в каждой `CourseCard` и `memo`-граница `Results`. Настройки нагрузки (240 карточек, 80 000 итераций) те же в обоих режимах.

- `App.jsx` — два независимых state: `text` (значение input) и `listQuery` (запрос, по которому строится список). Переключатель режима:
  - **Обычный** — `setText` и `setListQuery` вызываются срочно, в одном обработчике.
  - **Transition** — `setText` вызывается срочно, а `setListQuery` внутри `startTransition`. `isPending` показывает «Список обновляется…» и делает список полупрозрачным.
- Управляемый input никогда не обновляется внутри transition: `setText(value)` стоит до `startTransition` и вне его.
- `Results.jsx` — `memo`-список. Пока идёт срочный render с новым `text`, `listQuery` прежний, поэтому `Results` не пересчитывается. Над списком выводится запрос, по которому он построен, и число найденных.
- `timing.js` — замеры: время от `event.timeStamp` до commit поля ввода (`useLayoutEffect` на `text`), число commit списка и время до последнего. Результаты пишутся прямо в DOM, а не в state, чтобы замер не добавлял своих render. Режим и кнопка «Сбросить замеры» обнуляют счётчики.

## Наблюдения

Production-сборка React, Chrome, обычный настольный ПК. Ввод по одной клавише подряд, одни и те же последовательности в обоих режимах. Цифры зависят от машины и скорости ввода, это наблюдение, а не гарантия ускорения.

| Последовательность | Режим | Ввод → commit поля (средн. / макс.) | Commit списка |
|---|---|---|---|
| `react 12` + 3×Backspace (11 нажатий) | обычный | 6.2 / 13.5 мс | 11 |
| то же | transition | 0.3 / 0.6 мс | 2 |
| `c⌫ s⌫ t⌫ c⌫ s⌫ t⌫` (12 нажатий, каждый ⌫ возвращает все 240 карточек) | обычный | 17.5 / 19.8 мс | 12 |
| то же | transition | 0.2 / 0.4 мс | 0 |

- В обычном режиме поле и список коммитятся вместе, поэтому символ появляется только после render всего списка. Задержка поля растёт вместе с размером списка.
- В transition поле коммитится сразу, а render списка идёт с низким приоритетом. Если пришло новое нажатие, React бросает незавершённый render списка и начинает заново с последним `listQuery`. Поэтому промежуточные списки не коммитятся (2 commit на 11 нажатий).
- Transition не ускоряет сами карточки: на одно построение списка уходит столько же работы. Меняется только порядок: ввод больше не ждёт список.
- Во второй последовательности финальный запрос пустой, как и начальный, поэтому список не коммитился ни разу. При этом на экране правильный результат: «», 240 карточек.
- `isPending` во время ввода показывает «Список обновляется…», после завершения возвращается «Список готов».

## Самопроверка

- Набрать `typescript 1`: поле обновляется сразу, затем список показывает запрос «typescript 1» и 36 карточек, индикатор «Список готов».
- Очистить поле (Ctrl+A, Backspace): поле пустое, список показывает «» и 240 карточек.
- В режиме transition `setText` вызывается вне `startTransition` (см. `handleChange` в `App.jsx`).
