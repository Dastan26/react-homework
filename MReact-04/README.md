# MReact-04. Отложенное значение и старый результат

React 19.3.1, Vite 8.3.8, Node 24.

```bash
npm install
npm run dev -- --host 127.0.0.1
```

Страница: https://dastan26.github.io/react-homework/MReact-04/

## Что сделал

За основу взята лаборатория MReact-03: та же нагрузка в отдельных карточках, та же `memo`-граница `Results`, режимы «Обычный» и «Transition» остались. Добавлен третий режим **Deferred**.

- В режиме deferred вместо двух поисковых state используется `text` и `deferredText = useDeferredValue(text)`. `listQuery` в этом режиме не обновляется.
- В `Results` передаётся только `query={deferredText}`. Свежий `text` дополнительным prop в список не уходит, поэтому при срочном render с новым `text` `memo` пропускает список: его единственный prop не изменился.
- Над списком выводится «Результаты для запроса: «…»» — это запрос, по которому список реально построен (`deferredText`), а не то, что сейчас в поле. Старые результаты подписаны старым запросом.
- Если `text !== deferredText`, рядом с полем выводится «Обновляем результаты», а список становится полупрозрачным. Когда отложенный render завершился — «Результаты актуальны».
- При смене режима поле и запрос сбрасываются, чтобы режимы стартовали с одинакового состояния.

## Отличие от debounce

- Debounce ждёт фиксированную паузу (например, 300 мс) после последнего нажатия и только потом обновляет список. Задержка есть всегда, даже на быстрой машине, а на медленной её может не хватить, и render всё равно заблокирует ввод.
- `useDeferredValue` не ждёт таймер. React сразу коммитит срочное обновление поля, а затем в фоне начинает render списка со свежим значением. На быстрой машине список отстаёт на один кадр, на медленной — дольше. Если пришло новое нажатие, незавершённый фоновый render выбрасывается и начинается заново с последним значением.
- Debounce уменьшает число render. Deferred не уменьшает объём работы одного render, а меняет приоритет: ввод не ждёт список.

## Ограничение для одного длинного синхронного цикла

React может прервать фоновый render только между компонентами: после каждой единицы работы он проверяет, не пришло ли срочное обновление. Здесь нагрузка разбита на 240 карточек по ~0.1 мс, поэтому React успевает уступить ввод между ними.

Если вся работа — один длинный синхронный цикл в одном компоненте (например, один render или `useMemo`, который считает 300 мс), прервать его посередине нельзя. Пока цикл идёт, главный поток занят, и ввод ждёт его окончания и в режиме deferred, и в transition. В таком случае нужно уменьшать саму работу: разбить на части, кешировать, перенести вычисление в Web Worker.

## Самопроверка

Production-сборка React, Chrome. В режиме deferred набрал `css` по одной клавише, затем очистил поле. Состояния, которые React закоммитил (поле | подпись списка | статус):

```
c   | «»    | Обновляем результаты
cs  | «»    | Обновляем результаты
cs  | «cs»  | Результаты актуальны
css | «cs»  | Обновляем результаты
css | «css» | Результаты актуальны
""  | «css» | Обновляем результаты
""  | «»    | Результаты актуальны   (240 карточек)
```

- Пока список старый, он подписан своим старым запросом, а рядом стоит «Обновляем результаты».
- Список для промежуточного «c» не строился: отложенное значение сразу перешло к «cs».
- После очистки список показывает «» и 240 карточек.
- Режимы «Обычный» и «Transition» работают как в MReact-03.
